# 第一阶段：实时对话与行为调整

日期：2026-09-18。范围：`apps/realtime-home`。

第一阶段的目标包含 **realtime**。能自主活动、调用模型、保存人格和记忆，只说明基础闭环成立。还需要确认用户说话、改口或打断时，Agent 能及时响应，而且世界的行为确实随之改变。本阶段仍保留语音设备与识别链路的实际验收项，不能用接口成功或演示动画代替。

## 交互方式

文字可以连续发送，不需要等上一个 HTTP 请求、模型回复或动作结束。收到新消息后，页面同步“听到了，正在调整下一步”；服务端暂时保持当前动作的位置和进度，交给 Jev 选择继续、换动作或停止。合法新动作从实际位置重新寻路，中断的旧动作不结算效果，也不推进旧愿望。

点击“开始实时对话”后，浏览器持续识别中文并展示正在听到的文字。稳定的最终识别结果短暂合并后自动发送，不再先填到输入框等待 Enter。中间识别假设不会执行；识别中断时，未识别完整的语句会丢弃并提示重说。用户开始插话时，立即取消本地朗读，并向服务端取消对应轮次的旧回复。新的完整语句到来后，仍由 Jev 选择行为。

“打断回复”只取消对应回复；要停止物理动作，可以直接说或发送“停止”。“结束实时对话”、世界暂停、断开家园连接或离开页面，会结束浏览器监听并停止朗读。识别权限被拒绝或网络错误会明确显示，不将失败状态显示成已接通。

语音输入与朗读使用浏览器 Web Speech 能力，并未接入端到端实时音频模型。语言模型输出仍是经过结构校验、由 Jev 采纳的完整短回复，没有用打字动画伪装流式模型输出。当前没有实现声学回声消除，使用耳机可避免扬声器里的 Milo 被再次识别；物理麦克风、识别服务和插话体验需要实机确认。

## 时序与旧请求处理

自主行为保留每 1,000 ms 的调度 tick。用户消息与对话回复返回可以唤醒同一个调度器；40 ms 的合并窗口用于消化接近同时到达的输入，但两次 Jev 请求开始仍至少间隔一秒。已有模型请求尚未结束、暂停或提供商退避时，唤醒不会绕过限制。取消请求后等待其 Promise 结束再释放槽位，不重叠请求，不补发错过的 tick，世界倍速不加速模型调用。

浏览器为每次输入生成递增序号，并携带当前世界 `epoch`。同浏览器旧请求迟到会返回 409，不能覆盖更新的意图；同序号、相同内容重试返回原收据，不重复产生经历或模型请求。排序状态有界保留 128 个浏览器会话，适用于当前本机共享世界。尚未提供跨用户持久化消息队列语义。

每条完整输入成为一个 `RealtimeTurn`。新输入使上一轮标为被替换，取消旧快慢请求，旧响应即使后来完成也不进入世界、回复或记忆。插话取消请求同时绑定世界和原轮次，迟到的取消消息不能误伤更新的对话。前端取消旧朗读队列并忽略过期播放回调；失败或迟到的旧 HTTP 响应不会清空刚输入的新草稿。

有兼容的新问题时，Jev 可以保留当前动作并按需唤醒 LLM。行为推进和回复生成可以同时进行，用户无需等待回复再改口。LLM 不能自行更换动作或将建议标成执行成功。

## 测量与验收

`WorldState.turns` 保留最近 32 轮的时间戳，事件也关联 `turnId`。页面对话区展示行为响应时间，思考区展示更细的阶段时间，导出运行记录时一并保留。

| 指标 | 含义 |
| --- | --- |
| 页面 HTTP 往返 | 浏览器发送开始到收到服务端收据，使用浏览器单调时钟 |
| `decisionAt - receivedAt` | 服务端接收到首个有效 Jev 决策，包括调度等待和模型调用 |
| `appliedAt - receivedAt` | 接收到开始、继续或停止动作；不等于动作完成时间 |
| `replyAt - receivedAt` | 接收到结构有效并经 Jev 采纳的自然语言回复 |
| `browserObservedMs` | 真实页面按 Enter 前至该轮 SSE 结果在页面呈现；断言匹配轮次 ID 和该轮时间标签，包含网络、轮询与页面确认开销 |

服务端指标使用同一时钟，不拿浏览器时钟直接相减。它们不包含人说话的时长、语音识别等待、扬声器播放延迟。不能把 40 ms 唤醒合并时间说成模型反应时间，也不能把收到消息时的动作暂缓当成已完成语义理解。

本轮真实测试为动作响应设定 3 秒、短对话回复设定 5 秒的单样本预算。场景在 **1× 世界速度** 下执行，调用已有真实 TypeSafe 与 DeepSeek 配置，不替换模型选择。该预算用于发现明显迟缓，不是 P95 性能指标或所有输入都能成功的保证。

整组真实回归于本日通过，共 10 项（原有 6 项与本轮 4 项），耗时约 1.4 分钟。随后将页面观察断言绑定到对应轮次的 SSE 结果，重新运行这 4 项 realtime 场景，全部通过，耗时 19.9 秒。下面使用这次最后复跑的数据，不混入前一轮数值：

| 场景 | 服务端响应 | 浏览器观察到结果 |
| --- | --- | --- |
| 开始去卧室睡觉 | 699 ms | 740 ms |
| 走路途中改去厨房喝水 | 855 ms | 928 ms |
| 喝水交互途中改去书房看书 | 335 ms | 423 ms |
| 看书途中要求停下 | 921 ms | 969 ms |
| 第一轮自然对话的已采纳回复 | 1,597 ms | 1,693 ms |
| 下一轮自然对话的已采纳回复 | 2,135 ms | 2,224 ms |
| LLM 思考中连续改口，最终去看书 | 920 ms | 952 ms |
| 保持工作同时回答阅读偏好 | 2,647 ms（回复） | 2,742 ms |

动作切换场景中，三次旧动作均被中断，未产生完成效果；实际完成数为 0。连续改口场景中，旧 LLM 已开始请求，但被取消，最终没有显示旧问题的回复。自然对话使用两次真实 LLM 成功响应，世界没有启动物理动作。边工作边聊天时，动作的开始时间保持不变，位置继续推进，没有重复启动或中断。这些是最后复跑中的有限样本，后续复跑会更新 JSON 报告，不能混用不同轮次计算延迟统计。

扩大到“边工作边聊天”后，整组复跑曾出现一次失败：Jev 保留了工作动作并成功唤醒 DeepSeek，但 HTTP 200 的回复含非法 `suggestedActions`，严格校验将整条建议丢弃。检查代码发现，慢系统观察中也混入了快系统的 `continue` / `idle` 控制候选。现已将慢系统可见候选限制为物理活动，并明确普通对话、继续当前活动时不需要提出新动作。没有增加非法枚举、静默纠正返回值或放宽测试预算。失败时轮次标记回复错误，聊天区给出可操作提示，结构诊断保留在思考记录；对应失败报告保留在带时间戳的 JSON 中。

## 验证入口

从项目根目录执行：

```sh
pnpm test
pnpm test:e2e
pnpm --filter @realtime-agent/home test:live realtime.spec.ts
```

普通测试覆盖新输入暂缓动作、接近完成时不结算旧效果、单并发与最短请求间隔、取消后的结果隔离、输入序号、乱序 HTTP、自动语音最终结果、重复回调、未完整语句、权限错误、重连清理，以及桌面/390px 布局。语音回归中替换的是设备识别事件，页面、HTTP 与运行时走真实代码；它不证明音频已被识别。

本轮普通自动化合计 **102 项通过**（Home 77、Demo 19、共享配置 6）；浏览器回归 **9 项通过**（Home 7、Demo 2）。工作区类型检查与构建通过，最后修复后 Home 再次完成类型检查、构建及完整回归。既有 Three.js 分块体积提示与工具弃用提示保留，没有调整依赖或提高警告阈值。原生语音探测独立于这 102/9/10 项通过结果，其两次未通过记录见下文。

真实模型场景位于 `apps/realtime-home/tests/live/realtime.spec.ts`，包括走路与交互中的改令、连续对话、取消旧 LLM 后连续改口，以及保持动作同时回答兼容问题。报告位于 `apps/realtime-home/test-results/realtime/`，包括模型响应收据、每轮时间、实际动作和错误。失败尝试另存带时间戳的诊断，不能用旧成功报告覆盖当前失败结论。原有自主生活、身体恢复、顺序指令和人格连续性场景仍由 `pnpm test:live` 一起回归。

原生识别探测单独使用 `playwright.voice.config.ts`，需要先准备 16-bit PCM WAV，并通过 `VOICE_TEST_AUDIO` 指向文件，然后在 Home 目录运行：

```sh
pnpm exec playwright test --config playwright.voice.config.ts
# 有界面浏览器，同一测试录音：
VOICE_TEST_HEADED=1 pnpm exec playwright test --config playwright.voice.config.ts
```

这条探测用录音经 Chrome 测试采集设备进入真实识别 API，不注入 JavaScript 转写结果，也不等同于物理麦克风验证。结果单独写入 `native-voice-headless.json` / `native-voice-headed.json`。探测依赖本机浏览器和识别服务，未通过时必须保留其实际错误或无结果状态。

本日实际运行了无界面和有界面两次原生探测，均在 20 秒内没有收到转写结果，未产生任何 `source=voice` 的轮次，结果为 **未验证通过**。有界面记录包含 `start`、`audiostart`、`audioend`、`error` 和重连事件，没有 `speechstart` 或 `result`。仅凭这些记录不能断定是采集设备注入、系统权限还是识别服务的问题；不能据此宣称用户的实际麦克风不可用，也不能将这两次失败混入通过的浏览器事件回归。

## 第一阶段剩余验收

仍需在实际麦克风和耳机上确认：正常连续说话能够稳定识别；Milo 朗读时插话能停止旧声音；用户口头改令后动作在可接受的端到端时间内切换。此处的端到端时间从用户说完算起，应包含识别服务等待。

还需扩大措辞与环境变化样本，验证模糊改口、长句中自我修正、识别错误及网络抖动下的表现。当前结论应表述为“文字对话和真实模型行为改令已有实测，实时语音链路已实现并待设备/服务验收”，而不是宣布第一阶段全部完成。
